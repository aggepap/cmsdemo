02 · Database schema & migrations

Checks the database the CMS builds for itself: the migration chain and its tracking table, charset and server settings, every one of the 51 application tables (columns, indexes, unique keys and foreign keys), whole-schema invariants, the rows the seed commands write, and data integrity after the other checklists have been run. You need a MariaDB/MySQL client connected to the test database (all queries use DATABASE(), so select it first with USE <name>;), a terminal in the project folder, and permission to create and drop a scratch database. Expected values come from src/cms/db/adapters/mysql/schema/ and migrations/meta/0024_snapshot.json; where the code and docs/dev-guides/02-database.md disagree, the code wins.

Migrations

Run these against the test database after npm run db:migrate (checklist 01, cases SET-009/010). The migration runner is src/cms/db/migrate.ts, which calls Drizzle’s MySQL migrator over the app’s own connection. Drizzle records each applied migration in the table __drizzle_migrations (columns id, hash, created_at) and decides what to apply only by comparing the journal timestamp when with the newest created_at in that table.

Reading the expected column tables in this checklist. Types are written the way MySQL 8 prints COLUMN_TYPE. MariaDB differs only in display: int shows as int(11), bigint as bigint(20), tinyint as tinyint(4), and json shows as longtext (MariaDB’s JSON is an alias of LONGTEXT with a json_valid check). tinyint(1) is a boolean column on both. In COLUMN_DEFAULT, MariaDB wraps string defaults in quotes ('draft'), prints current_timestamp() and prints the word NULL for nullable columns without a default; MySQL 8 prints draft, CURRENT_TIMESTAMP (with DEFAULT_GENERATED in EXTRA) and an SQL NULL. Treat those spellings as equal. “none” means the column is NOT NULL with no default (MariaDB: SQL NULL in COLUMN_DEFAULT). For foreign keys, NO ACTION and RESTRICT behave the same in InnoDB; either passes. The primary key always appears as PRIMARY in the index query, whatever name the migration gave it. An index marked “added by InnoDB for the foreign key” is not in the migrations: the server creates it, named after the constraint, because no declared index starts with that column.

Server version and timestamp mode suit the schema

  1. Run the SQL below.
SELECT VERSION(),
       @@explicit_defaults_for_timestamp,
       @@default_storage_engine,
       @@innodb_default_row_format,
       @@sql_mode;

Expected:

  • The version is MariaDB 10.5 or later, or MySQL 8.0.13 or later (the migrations use expression defaults such as DEFAULT (now())).
  • @@explicit_defaults_for_timestamp is 1. The migrations declare nullable timestamps as a bare timestamp; with this setting at 0 (the default on MariaDB 10.9 and older) the server silently makes them NOT NULL and gives the first one in each table an automatic default and on-update. If it is 0, mark Fail and still run the timestamp case below to see the damage.
  • @@default_storage_engine is InnoDB.
  • @@innodb_default_row_format is dynamic (needed for unique keys on varchar(512) utf8mb4 columns such as documents.canonical_path).
