CMS manual QA

03 · Content: collections, documents & publishing

Creating, editing, publishing and deleting content in the admin: Pages, Brands, Testimonials and Popups, every field type the editor offers, slugs and automatic redirects, draft / published / scheduled / archived, translations, version history, edit conflicts and edit locks, draft preview, the unsaved-changes guard, the list screen, content permissions, shortcodes, markdown import, and how all of this shows on the public site (cache refresh, listing blocks, sitemap). SEO fields (checklist 06), forms and popups behaviour on the site (07), products (08) and experiences (09) are covered elsewhere. You need two browsers (or one normal and one private window), database client access and a terminal on the test machine.

Before you start

Checklist 01 must be done: migrations applied, the superadmin qa-admin@example.com exists, the seeded pages were published with npm run db:seed-site -- --force --publish-samples, and a second superadmin qa2@example.com (name QA Second) exists for the lock cases. Both EL and EN are ticked for Editing and Public in Settings → Languages. The URLs below use http://localhost:3002; on a hosted test environment use its address instead. The admin is at /admin. “Pages” in the sidebar opens /admin/page. Write down the id of each document you create: it is the number at the end of its edit URL (/admin/page/<id>).

  4. Sign in as each new user in the private window (complete two-factor setup if asked, see checklist 05).

Expected: Both roles and users are saved without error. Each new user lands on the dashboard and sees Pages and Brands under Content in the sidebar.

Pages: create, publish, edit, delete

Signed in as qa-admin@example.com unless a case says otherwise. Pages are public at /{slug} in Greek and /en/{slug} in English. A page that is not public redirects to /page-not-found (Greek heading Η σελίδα δεν βρέθηκε) or /en/page-not-found (Page not found).

Create a draft page

  1. Open Pages and click + New.
  2. Type QA Page One in Title, qa-page-one in Slug, QA required in QA text. Leave Status — EL on draft.
  3. Click Create Page.
  4. Run the SQL below.
SELECT id, slug, locale, status, canonical_path, published_at,
       JSON_UNQUOTE(JSON_EXTRACT(data, '$.title')) AS title
FROM documents WHERE type = 'page' AND slug = 'qa-page-one';
  • The New screen heading reads New Page. After the click you are on /admin/page/<id> with heading QA Page One and /qa-page-one beneath it; the status badge reads draft; Version history lists v1 (current).
  • SQL: one row, locale el, status draft, canonical_path /qa-page-one, published_at NULL, title QA Page One.
  • Opening /qa-page-one in a signed-out window lands on the not-found page.

Slugs & automatic redirects

A new or changed slug is normalised when saved: lower case, hyphens, Greek transliterated, at most 96 characters. Changing the slug of a live document writes a 301 from the old address (listed under SEO → Redirects). Use curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' <url> to see status and target.

“My Post” is saved as my-post

  1. Create a page titled My Post with slug My Post, QA text x, status draft, click Create Page.
  2. Look at the Slug box and the line under the heading.
  3. Change the slug to My Post Again and click Save EL; look at the Slug box without reloading.
  4. Run: SELECT slug, canonical_path FROM documents WHERE type = 'page' AND slug LIKE 'my-post%';

Expected: After step 1 the Slug box and heading line show my-post. After step 3 the box immediately shows my-post-again (not what was typed). SQL: slug my-post-again, canonical_path /my-post-again.

Ref: src/cms/core/documents/slug-input.ts · src/cms/core/slug.ts · src/cms/admin/document-save.ts (slugAfterSave)

Renaming a published page redirects the old address

  1. Open QA Page One (published). Change the slug to qa-page-renamed, click Save EL.
  2. Run the curl line from the intro for http://localhost:3002/qa-page-one and http://localhost:3002/qa-page-renamed.
  3. Run the SQL below and open SEO → Redirects in the admin.
SELECT source, target, status_code, kind, active, reason, notes
FROM seo_redirects WHERE reason = 'slug_change' ORDER BY id;
SELECT slug, canonical_path FROM documents WHERE id = <QA Page One id>;
  • curl: /qa-page-one answers 301 to …/qa-page-renamed; /qa-page-renamed answers 200.
  • SQL: a row /qa-page-one → /qa-page-renamed, 301, literal, active 1, reason slug_change, notes Auto: the page’s address changed — old links are sent to the new one. The document's canonical_path is /qa-page-renamed.
  • The redirect is listed on the SEO screen with that note.

The scheduler publishes a due document

Preconditions: QA Scheduled's time has passed. Do not open the Pages list or its editor after that time (opening them also publishes it, see the next case).

  1. Run curl -s -X POST -H "x-cron-secret: <your CMS_CRON_SECRET>" http://localhost:3002/api/cms/cron/content-publish-scheduled.
  2. Open /qa-scheduled signed out.
  3. Run the SQL below.
SET time_zone = '+00:00';
SELECT status, published_at, scheduled_for FROM documents WHERE slug = 'qa-scheduled';
SELECT actor_label, action, created_at FROM audit_logs
WHERE action = 'document.publish_scheduled' ORDER BY id DESC LIMIT 1;
  • curl prints {"ok":true,"data":{"status":"ran","result":{"published":1,"failed":0}}}.
  • The public page shows QA Scheduled.
  • SQL: status published, published_at equal to scheduled_for; an audit row with actor_label scheduler.
  • Running the curl again prints "published":0.
