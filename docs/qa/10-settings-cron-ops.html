10 · Settings, scheduled jobs & operations

Running a site rather than editing it. Covered here: the Settings screen as a whole (its tabs, the one Save settings that sends only what changed, changes taking effect without a restart, the settings cache), every settings group and every key in it, server-side validation and the all-or-nothing save, who may view and who may change settings, the language-settings API; the scheduled-job endpoint POST /api/cms/cron/<job> and each of its seven jobs, the cron secret, overlap protection, rate limits and the suggested crontab; the two older per-job endpoints; the CMS updater's rules on what is replaced and what is kept; the environment-variable reference; a post-deploy smoke test; a backup and restore drill; logs, audit and 404-log growth; the documentation builds; and the release gate. Covered elsewhere and referenced by ID: install, env file, migrations and seeds (SET-001 to SET-023), production build and the X-Real-IP rule for sign-in (SET-030, SET-031), module switches (SET-033 to SET-043), language switches on screen (SET-044 to SET-049), the edit-lock relay (SET-059 to SET-065), building an update package and the first updater checks (SET-066 to SET-072), security headers and robots.txt (SET-073 to SET-078), the shipped PDFs (SET-079, SET-080), the site_settings table (DB-020), Settings keyboard use and unsaved-changes guard (ADM-044, ADM-051), “Require two-factor authentication” (AUTH-027, AUTH-028), the audit screen (AUTH-063 to AUTH-067), public rate limits and stored secrets (AUTH-071 to AUTH-078), branding (MED-030 to MED-034), structured data (MED-082 to MED-096), SEO fields (MED-073 to MED-077), sitemap and robots extras (MED-080, MED-081), the 404 log screen (MED-060 to MED-066), GA and cookies (MKT-067, MKT-079), and the per-module settings in checklists 08 and 09. You need: a test environment (a local production build is enough for most cases, a hosted staging box with shell access for the deploy and backup suites), a terminal with curl, openssl, unzip and mysqldump, a database client, permission to edit the environment file and restart the app, and two browsers (or one normal and one private window).

Before you start

Checklist 01 must be done (migrations, seeds, superadmin qa-admin@example.com). Sign in as qa-admin@example.com unless a case says otherwise. URLs use http://localhost:3002 (npm run dev); a production build (npm run build then npm run start, see SET-030) answers on http://localhost:3000; on a hosted environment use its address. Admin paths assume ADMIN_PATH=admin.

Terminal. In the project folder run BASE=http://localhost:3002, and copy the admin cms_session cookie into S as described in checklist 05 (“Using curl with a session”). Once CMS_CRON_SECRET is set (OPS-025) also run CRON='<value of CMS_CRON_SECRET>'. Give every curl that is rate limited its own -H 'X-Real-IP: 10.10.0.N' (a new N per case) so cases do not use up each other's budget; restarting the app empties all rate-limit buckets.

Settings from the terminal. A settings change by API is:

curl -s -X PATCH "$BASE/api/cms/settings" -b "cms_session=$S" \
  -H 'Content-Type: application/json' -H 'X-Real-IP: 10.10.0.1' \
  -d '{"seo.sitemapExtraUrls":"https://example.com/qa-ops"}' -w '\n%{http_code}\n'

Settings in the database. Values are JSON (strings keep their quotes). The key column is called key and must be back-quoted:

SELECT `key`, value, updated_by, updated_at FROM site_settings ORDER BY `key`;

Caches. Settings reads are cached until a save purges them; they never expire on a timer. After changing site_settings directly in SQL, restart the app before looking at the result (OPS-005 shows why).

Write down the output of the site_settings query above before you start. OPS-066 puts the site back from it.
