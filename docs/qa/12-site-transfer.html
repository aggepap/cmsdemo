CMS manual QA

12 · Site transfer: export & import

Moving content, media and settings from one site built on this CMS to another through Export / Import. Covered here: who may open the screen and move each kind of data, choosing whole groups or single items, dependencies that come along and the ones you leave out, building and downloading a package, what a package contains (and never contains), the chunked upload and resuming it, refusal of damaged or hostile packages, languages, conflicts and the per-item choice, the dry run, running, stopping and resuming an import, what lands on the site (remapped links, copies, overwrites, drafts), the report, the audit entries and the cleanup job. Also the site-configuration tables: script snippets, cookie categories, shipping zones, Google review locations, redirects and per-path SEO meta. Also people and transactions: customer accounts, newsletter subscribers and suppressions, product reviews, orders, reservations, availability overrides, admin roles and users — with the personal-data and password safeguards. Gift cards are deliberately never transferred. You need: two test sites on this build (called SOURCE and TARGET; one site importing its own export also works for most cases), a database client for each, a terminal with curl, unzip and sha256sum, and two browsers (or one normal and one private window).

Before you start

Checklist 01 must be done on both sites. Sign in as the superadmin qa-admin@example.com unless a case says otherwise. Take a database backup of TARGET before the import suites (mysqldump --single-transaction, see OPS in checklist 10); XFR-062 restores it.

Test data on SOURCE. Create, in both languages: a product category qa-shoes with a parent category qa-root and an image; a size chart qa-chart; two products qa-red and qa-blue, each in qa-shoes, with the size chart, a gallery of two images, and each listing the other as a component/related product; a page qa-page whose body contains the paragraph [popup id="N"] for an existing popup N and a link to one of the images; a custom field on products limited to qa-shoes; a logo in Settings → Branding.

Terminal. BASE=http://localhost:3002 and the admin session cookie in S as described in checklist 05.

A second role. On each site create role qa-content with Access, View content, Edit content, Export site data, Import site data (no media, no settings, no publish) and user qa-content@example.com with it.

What is inside a package, and what never is

  1. unzip -l export.zip, then unzip -p export.zip manifest.json.
  2. Export Settings → Everything as well, and run unzip -p export.zip 'data/settings/*' | grep -c -i -E 'secret|baseline|oauthState|password'.
  3. For one data file listed in the manifest: unzip -p export.zip data/documents/product/0001.jsonl | sha256sum.
  • Entries: manifest.json, data/…/0001.jsonl files, data/stubs.json, media/<uuid> (and .avif companions).
  • The manifest has "format": "cms-transfer", formatVersion, cmsVersion, the source locales, a count per group and a sha256 per file; step 3 matches it.
  • Step 2 prints 0: no service credentials, no edit baselines, no OAuth state. Payment keys, Google tokens and passwords are never in a package.

Damaged and hostile packages are refused

  1. Upload a random .zip that is not an export (e.g. zip a text file).
  2. Unzip an export, change one character in a data/…jsonl file, zip it again and upload it.
  3. Upload a zip whose entry is named ../evil.txt (python3 -c "import zipfile;z=zipfile.ZipFile('slip.zip','w');z.writestr('../evil.txt','x')").
  4. Upload a zip holding one 50 MB file of zeros (head -c 50000000 /dev/zero > z; zip bomb.zip z).

Expected: Each is refused with a message in the red box and nothing is written to the site: 1 “This is not a site export package (no manifest).”; 2 “… does not match the manifest — the package is damaged.”; 3 “This is not a readable package: Unsafe entry name…”; 4 “… implausible compression ratio.” No file named evil.txt appears anywhere on the server.

Ref: src/cms/core/transfer/zip-file.ts · import/package.ts

A package over the size limit, or sent out of order, is refused

  1. curl -s -X POST "$BASE/api/cms/transfer/imports" -b "cms_session=$S" -H 'Content-Type: application/json' -H "Origin: $BASE" -d '{"filename":"big.zip","size":99999999999}' -w '\n%{http_code}\n'
  2. Open a normal upload (size 20) and send curl -s -X PUT "$BASE/api/cms/transfer/imports/<id>/chunk?offset=10" -b "cms_session=$S" -H "Origin: $BASE" --data-binary 'abc' -w '\n%{http_code}\n'.
  3. The same request with Origin: https://evil.example.

Expected: 1: 422 “The package is too large (limit … MB).” 2: 409 with "issues":{"offset":0}. 3: 403 “Cross-origin request rejected.”

Running an import

New items arrive with their links pointing at this site's items

  1. On a TARGET without the QA data, import the package from XFR-013 with everything new. Run it and confirm.
  2. Open qa-red on TARGET: its category, size chart, component product and gallery. In SQL compare JSON_EXTRACT(data,'$.categories') with the id of qa-shoes on TARGET.
  3. Check SELECT * FROM document_relations WHERE from_id = <qa-red id>.
  • All items are created; both languages of each product are one translation group; the products are drafts unless “Keep published content published” was ticked and you have Publish content.
  • The category id in data is TARGET's id of qa-shoes, not SOURCE's; the size chart, qa-blue and every image resolve; document_relations has rows for the relation fields.

Housekeeping

Old jobs are removed by the scheduler

  1. List .data/transfers/ (or CMS_TRANSFER_DIR). Set CMS_TRANSFER_TTL_HOURS=0.001, restart, wait a few seconds.
  2. curl -s -X POST "$BASE/api/cms/cron/transfer-cleanup" -H "x-cron-secret: $CRON"

Expected: The response is {"ok":true,"data":{"status":"ran","result":{"removed":N}}} and the job folders are gone. Restore the TTL afterwards.
