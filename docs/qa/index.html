CMS manual QA

Checklists a human tester works through to confirm every part of the CMS works, from install and database schema to the admin, the shop, bookings and the public site.

Checklists

How to use these pages

  1. Fill in your name, the environment URL and the build or commit at the top. They are saved in this browser and included in every export.
  2. Open a checklist. Each case has an ID, a priority, preconditions, steps and the expected result.
  3. Work through the steps, then mark the case Pass, Fail, Blocked (you could not run it) or N/A (the feature is off on this site). Click a pressed button again to clear it.
  4. For every Fail, write what happened in the notes: the actual result, the URL, and a screenshot or defect link.
  5. Use Export CSV or Export JSON to hand results over. Results are stored only in this browser; clearing site data or switching browsers loses them.

Priorities. P1 is the smoke set: run it on every release and after every deploy. P2 covers the core behaviour of each feature: run it before a release. P3 covers edge cases and hardening: run it for major releases or after changes in that area.

Filter a page by priority to run only the smoke set.

Before you start

  • Use a test environment, never production. Several cases create orders, send email, take payments in sandbox mode and delete data.
  • Set up the site as described in docs/LOCAL_SETUP.md or docs/STAGING-SETUP.md, with migrations applied and the seeds run (checklist 01 walks through this).
  • Payment providers must be in sandbox / test mode. Use each provider's published test cards.
  • Have a mailbox you can read for the admin address and a second one to act as a customer.
  • Have database access (a MySQL/MariaDB client) for checklist 02 and for the cases that check stored rows.
  • Create these accounts before running role tests: a superadmin, an editor, and a custom role with only a few permissions (checklist 05 explains how).
  • Test in at least one Chromium browser and Firefox; run the public-site checks on a phone-width window too.
  • If a module is switched off on the site under test (shop, booking, newsletter), mark its cases N/A, but still run the case that checks the module is hidden when off.

Reporting a failure

A useful defect report has the case ID, the environment and build from the top of the page, the exact steps you took if they differ from the case, what you expected, what happened, and a screenshot. For server errors include the time so developers can find the log line.

The technical background for each area is in docs/dev-guides/; the end-user explanations are in docs/user-guides/.

Results are saved in this browser only. Export them before clearing browser data.
